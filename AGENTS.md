# AGENTS.md — agent-factory

Verified 2026-11-20. This repo builds `/factory`: a harness-neutral orchestrator (`core/`) plus
per-harness adapters (`adapters/`) rendered into installed files by Python tooling. The product is
Markdown prompts; the tooling is Python 3 stdlib.

## Layout

- `DESIGN.md` — source of truth for flow behavior. Behavior changes are recorded here FIRST, then
  carried into `core/` and `adapters/`. `CONTEXT.md` is the domain glossary; use its terms, one
  term per concept. `docs/adr/` holds architecture decisions.
- `core/` — harness-neutral: `skills/factory/SKILL.md` (orchestrator loop, neutral verbs only),
  `skills/factory/bin/factory` (run-state CLI, the single state writer), `skills/factory/references/`
  (verbs, state, protocol, findings, `engineering.md` ENG-1..31, design-code maps), `roles/` (12 role prompts).
- `adapters/<harness>/` — `harness.md` + `adapter.json` per harness: claude-code, opencode, codex, copilot, zcode.
- `tools/` — `render.py` (builds `dist/<harness>/`), `bench.py`, `tests/` (unittest suite + one `node:test` file).
- `dist/` — GENERATED by `tools/render.py`. Never edit by hand, never commit; CI fails if tracked.
- `.agents/skills/` + `skills-lock.json` — the skill library managed by the `skills` CLI: vendored
  third-party skills plus the factory-authored skills (`create-project-agents-file`,
  `design-to-code`, `pen-design`, `prompt-optimiser`) kept there as `sourceType: local` entries;
  `.agents/LICENSES/` holds upstream licenses (ADR 0019). Do not hand-edit vendored skills; the
  factory's local skills are edited in place.
- `core/skills/` — the orchestrator only (`skills/factory/` with `bin/factory` and `references/`).
  Every other skill lives in `.agents/skills/` and is linked by the installer from there; the
  renderer emits no `dist/<harness>/skills/`.
- `conformance/` — bench fixtures and golden runs. `specs/` — SpecKit specs per factory feature.
- `.factory/config.json` — this repo's own factory-run config: instruction references and per-tier models.
- `.specify/memory/constitution.md` — v2.0.0, five principles; supersedes other practices in this repo.

## Build / Configuration

- Python 3 required; stdlib only, nothing to pip install. Node only for the trigger-hook test and the
  design-to-code trigger itself.
- Render one harness (point `FACTORY_HOME` at a temp dir so you never touch a real install):

```sh
FACTORY_HOME="$(mktemp -d)" python3 tools/render.py claude-code
```

- List harnesses: `python3 tools/render.py --list` → claude-code codex copilot opencode zcode
- After any `core/` or `adapters/` change, render ALL five (Constitution III):

```sh
export FACTORY_HOME="$(mktemp -d)"
for h in $(python3 tools/render.py --list); do python3 tools/render.py "$h"; done
test -z "$(git ls-files -- dist/)"
```

## Testing

- Full suite, ~9 min, 739 tests: `python3 -m unittest discover -s tools`
- One module: `cd tools && python3 -m unittest tests.test_state -v` (module path is `tests.<name>`;
  render tests are the exception, at the tools root: `cd tools && python3 -m unittest test_render -v`)
- One test: `cd tools && python3 -m unittest tests.test_totals.UsageLabellingTests.test_estimates_sum_under_their_own_labels -v`
- Filename filter: `python3 -m unittest discover -s tools -p test_state.py`
- Trigger-hook test (node): `node --test tools/tests/test_design_to_code_trigger.mjs` (7 tests, <1 s)
- Add-a-test recipe: create `tools/tests/test_<topic>.py` with `unittest.TestCase` classes;
  discovery picks it up, no registration step. Verified with a scratch test this session (ran, then deleted).
- Suite green as of 2026-11-20: the in-flight first-party-skills move completed as ADR 0019
  (local lock entries, no `dist/<harness>/skills/`); the 7 red tests it caused are fixed.

## Code style and conventions

- No linter, formatter or type checker is configured. Python tooling uses stdlib unittest; match the
  file you edit (type hints where the surrounding code uses them).
- Markdown is the product. Constitution Writing Standards: short, imperative, unambiguous; one idea
  per sentence; one term per concept, taken from `CONTEXT.md`.
- Constitution II: files under `core/` NEVER name a harness tool, path or command — only the neutral
  verbs in `core/skills/factory/references/verbs.md` (`SPAWN`, `SPAWN_PARALLEL`, `ASK`, `NOTIFY`,
  `RESOLVE`, `SHELL`, `WEB_SEARCH`, `WEB_FETCH`). Harness specifics belong in `adapters/<harness>/`.
- Constitution IV: agents are stateless across turns; anything a later turn needs lives in
  `state.json` (written only via `core/skills/factory/bin/factory`) or on disk. Agents never talk to
  the user; questions go through the orchestrator's relay.
- Constitution V: YAGNI — extend an existing rule, role or script before adding a new one.
- Constitution changes go through `/speckit-constitution` with a version bump, committed together
  with any implied `DESIGN.md` change.
- Code-delivery roles follow `ENG-1..ENG-31` (`core/skills/factory/references/engineering.md`):
  test-first with a `Red:` line in the commit body, seams fixed at plan time, KISS/YAGNI.

## Gotchas

- `git ls-files -- dist/` must stay empty — CI gates on it.
- CI runs exactly three gates: the full unittest suite, render-all-five + dist-untracked,
  `bash -n install.sh`.
- The full suite takes ~9 minutes: run the module you touched first, the full suite before claiming done.
- `install.sh` writes into real harness directories (`~/.claude`, `~/.config/opencode`, …) — never run
  it as a test.
- Read `CONSTRAINTS.md` before writing code. Do not weaken it to make a change pass.

# Base Agent Rules

## 1. Session Init

Invoke `/caveman ultra` on the first message of a session, before any other output. Once per
session only.

## 2. Ambiguity Handling

**Trigger** — input shows any of: no stated platform/framework/runtime; goal without a measurable
outcome; two or more incompatible readings; open "how to X" with no bounded deliverable;
unprioritised feature list; typos or fragments that block parsing.

**Then, in order:** invoke `/prompt-optimiser full` → display the optimised prompt verbatim →
confirm direction (ask only when a decision still changes the implementation) → proceed.

State in the same response that `/prompt-optimiser full` ran and why. Never substitute your own
interpretation for the optimiser output.

## 3. UI Change Critique Loop

**Trigger** — any edit to: component/view files (`.tsx .jsx .vue .razor .cshtml .html .svelte
.xaml .axaml`); templates, markup, or partials rendered to a screen; stylesheets (`.css .scss .less`) or
utility-class markup; design tokens, theme, or Tailwind config; layout, spacing, typography,
colour, or motion; user-visible copy, labels, error messages, empty states, or i18n strings.

**Then, before declaring the task complete:**

1. Invoke `/impeccable critique` on the changed UI. Pass the changed files and the user-facing intent.
2. List every returned recommendation with its priority.
3. Implement each one that is actionable in scope and does not contradict an explicit user
   constraint.
4. Run `/impeccable audit` on the updated UI to catch issues that survive the first pass.
5. Run `/impeccable typeset` to validate hierarchy, typography, spacing, and reading rhythm.
6. Run `/impeccable polish` to finalise the visual consistency and quality pass.
7. Re-verify: re-read the edited files, confirm each implemented item is present, and confirm the
   change still builds or renders via the project's existing command.
8. Report which recommendations were applied and which were deferred, one line of justification
   per deferred item.

**Cap** — two critique-and-fix iterations per change set. If high or critical findings remain
after the second, stop, list them, escalate to the user.

**Never** — declare a UI task complete without at least one `impeccable` critique; surface
recommendations without acting on the actionable ones; expand scope beyond the changed surface.

## 4. Research

Before any non-trivial framework, library, SDK, API, or config decision, query Context7. For
Microsoft technologies (.NET, Azure, ASP.NET Core, EF Core, M365, Windows), also query Microsoft
Learn. Cite title and URL when a decision depends on retrieved docs. If no reliable source is
found, state what was checked, take the conservative option, and name the validation step.

## 5. .NET Standards

Nullable reference types on; `async`/`await` end to end with no `.Result` or `.Wait()`; DI over
static state; `IOptions<T>` for config; structured logging via `ILogger<T>`; `CancellationToken`
propagated on async APIs; file-scoped namespaces. Match the repo's existing style and target
framework. Run only build/test/lint commands that already exist.

## 6. Output Discipline

Every response line must carry information the user asked for or directly needs. Silence is always preferred over noise.

Never emit:
- Status narration ("I'll now look at…", "Let me check…", "I've updated X")
- Redundant confirmations ("Done!", "Sure!", "Of course!", "Understood")
- Filler transitions ("Moving on to…", "Next up…", "As a next step…")
- Unprompted commentary ("Interesting problem", "Good question!")
- Re-stating what the user said before answering
- Announcing tool calls before making them

When in doubt: omit it.

## 7. Precedence

Explicit user instruction this turn > repository instruction files > this file. On conflict,
follow the higher rule and state the conflict in one sentence.
