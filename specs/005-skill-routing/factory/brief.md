# Brief: factory skill routing

Implement the approved design in `docs/superpowers/specs/2026-10-25-factory-skill-routing-design.md`: route each external skill to the factory stage and role that should use it — `brainstorming` for exploratory ideas, `grilling` for concrete features, `ponytail` and `tdd` for code-build and fixer, and impeccable audit/critique for UI review — while keeping the factory's engineering rules, stateless roles, saved answers, worktree isolation, independent verification and approval gate. The design doc is the authoritative scope (its "Files to align" list and "Acceptance scenarios").

## Decisions

- The design doc is treated as approved and implemented as written.
- `brainstorming` is a logical skill name resolved through the adapter's `RESOLVE`, on the idea path only. Missing: the idea path pauses with setup guidance (install the superpowers `brainstorming` skill); no fallback to another skill, nothing auto-installed. The feature path never needs it.
- Intake routing: the orchestrator classifies the request text. Explicit exploration wording routes to brainstorming; explicit delivery wording or a spec link routes to grilling; an ambiguous request gets exactly one intent question (explore vs deliver). No new command flag.
- Idea path: `brainstorm → grill → worktree → existing spec chain`. The feature path starts at `grill`. Grilling reuses settled brainstorming answers.
- A user who stops after brainstorming leaves the pending run at `status: paused`, `stage: grill`, with the direction in the pending brief; `resume` continues into grilling. Nothing is written to the invoking checkout during intake. `brainstorm` joins the stage vocabulary; existing states stay readable.
- `ponytail` and `tdd` are resolved before a code-delivery run and their absolute paths are passed to every fresh code-build and fixer spawn; missing ones stop affected work with setup guidance. On resume, missing names are resolved and paths re-resolved when the harness changes.
- Ponytail runs at its default `full` intensity, bounded by the approved spec and engineering rules: it never removes requirements, security, accessibility, planned tests, repository tooling or ENG evidence, and does not replace the role envelope.
- TDD contributes technique (behavioural tests at public seams, vertical slices, boundary mocking). Engineering rules ENG-1..ENG-31 stay authoritative; the refactor-while-green conflict is resolved in their favour and stated explicitly. Skill-relative references (TDD's `tests.md`, `mocking.md`) resolve from the skill's own directory.
- Test-seam confirmation: the spec-builder relays the plan's proposed seams through the orchestrator before implementation as a question with `requires_user: true`. Fast mode never auto-answers `requires_user` questions; legacy questions without the field keep current behaviour. Confirmed unchanged seams are not re-asked on resume; changed seams need a new decision. A plan with no testable seams (all `Exempt:`) skips the confirmation.
- UI-diff detection: extend the path list with design tokens/themes (`tokens.*`, `theme*`, `*.resx`, `Styles/`, `Themes/`), UI assets (`*.svg`, icons/images under UI dirs) and locale/string files (`locales/`, `i18n/`, `strings*`); additionally the orchestrator judges a diff whose only change is user-visible copy in UI code as a UI diff. Backend-only diffs skip UI passes.
- UI reviewer: impeccable audit + critique, read-only, JSON findings, existing review/fix limits; discloses whether evidence was rendered or static. UX reviewer stays complementary.
- A compact shared skill-integration reference is added and linked from the orchestrator and code-writing roles. ADR 0001 is revised in place. DESIGN.md is updated first; README and product brief aligned. All harnesses are rendered canonically; `dist/` is never hand-edited; adapter model settings are not changed.
- Chain: `lite`, fast on (escalates to `full` on any CRITICAL/HIGH analyze finding).
