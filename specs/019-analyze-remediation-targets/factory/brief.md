# Brief: Enforce Analyze remediation targets

Implement `docs/superpowers/plans/2026-11-03-factory-analyze-remediation-plan.md`. The factory retains its first completed analyze report as a baseline, remediates findings in place, and refuses to enter implementation until a recheck meets baseline-relative acceptance targets: zero CRITICAL and HIGH, total and LOW each strictly below half their baseline counts, and any zero baseline count staying zero. Up to two automatic repair-and-recheck cycles run when targets are unmet; after that implementation stays paused until the user decides. A constitution amendment is applied only after explicit approval of its exact draft.

Chain: **lite** (fast mode on). Source of truth for code is `core/` (installed copies are rendered from it).

## Decisions

- Build and test commands (Q1): build renders all five harnesses into a temp `FACTORY_HOME`, checks `dist/` is untracked and runs `bash -n install.sh`; test is `python3 -m unittest discover -s tools` (matches `.github/workflows/ci.yml`).
- Baseline: `analyze-record` stores the first completed report's severity counts (plus report path and time) as `analyze.baseline`; later reports update only `analyze.result`. The baseline is preserved on resume and on lite-to-full escalation.
- Acceptance rule enforced in the implement transition gate (`checks.py`): CRITICAL == 0 and HIGH == 0; for total and LOW, a baseline of 0 requires a recheck of 0, otherwise `2 * recheck < baseline` (integer arithmetic, exactly half fails, odd baselines unambiguous). MEDIUM has no separate target beyond the total. Newly discovered findings count. Unanswered protected questions (`pending_clarify`, `requires_user`) keep blocking.
- Q2 — repair cycles: lite-to-full escalation on CRITICAL/HIGH is kept and consumes no cycle. Each remediate-plus-recheck cycle increments the existing `analyze.loops`; the cap is 2 per run on either chain, and applies when only MEDIUM/LOW remain unmet too (replacing today's lite "remediate once, then implement" and full-chain "loops < 2 on CRITICAL/HIGH" rules).
- Q3 — exhaustion: after two unsuccessful cycles the orchestrator shows baseline counts, latest counts and the unmet targets, and asks: one more guided pass, an explicit recorded `gate-override` (appears on the approver's veto list), or abort. The question is `requires_user: true`; fast mode never auto-answers it.
- Q4 — legacy runs without a baseline: derive it only when `analyze.reports` has exactly one entry and `analyze.result.report` names it; otherwise the gate refuses with a clear reason and the orchestrator asks the user to re-run analyze as a fresh baseline, override, or abort. Report markdown is never parsed for counts.
- Q5 — constitution amendments: remediate writes the exact proposed amendment, its rationale and version bump to `<spec_dir>/factory/constitution-amendment-<n>.md` and returns a `requires_user: true` question carrying the draft's hash. On approval a fresh remediate applies exactly that draft through the `speckit-constitution` amendment process after verifying the hash; then the cycle's recheck runs. Any change to the draft requires a new approval. Declined or missing approval leaves the constitution unchanged; the finding is fixed in the artifacts or stays counted.
- Q6 — every finding counts toward the total, including the non-blocking MEDIUM findings (ENG-10 unexplained new code, over-budget artifacts).
- Q7 — record the rule as ADR 0014 and update DESIGN.md, `references/state.md`, `SKILL.md` step 5 and `roles/spec-builder.md`.
- Acceptance examples to test: baseline 12 total / 6 LOW allows at most 5 total and 2 LOW with zero CRITICAL/HIGH; exactly half fails; odd and zero baselines behave as above; new serious findings block; resume keeps baseline and consumed cycles; declined/missing approval leaves the constitution unchanged; an approved amendment is followed by fresh analysis.
