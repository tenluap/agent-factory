# Software Factory: Design

Source of truth for how `/factory` behaves. `core/` and the adapters in `adapters/` are built from this document; when they disagree, fix them to match this one (or change this one first, deliberately).

Agreed in a grilling session on 2026-10-21. Harness model and stateless agents agreed on 2026-10-22. Skill routing agreed on 2026-10-25 (`docs/superpowers/specs/2026-10-25-factory-skill-routing-design.md`).

Pen design-code mapping agreed on 2026-10-25 ([approved contract](docs/superpowers/specs/2026-10-25-pen-design-code-mapping-design.md)).

## What it is

`/factory` is one user-invoked skill. Whichever agent session runs it becomes the **orchestrator**: it runs the loop below, spawns every agent, owns the run's state, and is the only thing that talks to the user. Agents never talk to the user directly.

The skill is global (installed into the harness's skill directory) and works in any git repo that has SpecKit (`.specify/`) installed.

## Harness model

The factory runs on any agent harness (Claude Code, OpenCode, Codex, GitHub Copilot, ZCode, ...). It is split into a portable core and thin per-harness adapters.

- **Core** (`core/`): the orchestrator `SKILL.md`, its references, the first-party skills in `core/skills/` (rendered verbatim into every `dist/<harness>/skills/`), and the role prompts in `core/roles/`. Core files never name a harness tool. They use the neutral **verbs** defined in `core/skills/factory/references/verbs.md`: `SPAWN`, `SPAWN_PARALLEL`, `ASK`, `NOTIFY`, `RESOLVE`, `SHELL`, and the role-only research verbs `WEB_SEARCH`, `WEB_FETCH`.
- **Adapter** (`adapters/<harness>/`): `harness.md`, which tells the orchestrator how to recognise the harness, how to perform each verb there, where skills and SpecKit commands live, and the harness's setup values; and `adapter.json`, which tells the renderer where to install and how to write native agent files (Markdown or TOML, fields, access, models).
- **One skill for every harness.** The installed skill is byte-identical on every harness and carries every adapter's `harness.md` under `references/harness/`. In preflight the orchestrator picks its own (`$FACTORY_HARNESS`, else the file whose "Recognise it by" line fits). This matters because harnesses read each other's skill directories (OpenCode reads `~/.claude/skills`, Copilot and Codex read `~/.agents/skills`): whichever copy a harness finds, it is the same skill. Only the agent files are generated per harness, by `tools/render.py`.
- **Adapters today**: `claude-code`, `opencode`, `codex`, `copilot` (CLI and VS Code agent mode; the github.com cloud agent is out of scope since it cannot relay questions), `zcode` (Z.ai's coding agent, desktop app or CLI). Every adapter supplies `deep` and `standard` model defaults in `adapter.json`. `${FACTORY_HOME}/config.json` overrides those defaults; an empty model value inherits the session's model.
- **Roles** carry neutral metadata (`tier`: `deep` | `standard`; `access`: `read` | `write` | `research`; optional `mode`: `primary`). The adapter maps tiers to models and access to tool lists. `research` is `read` plus web search and fetch, and no file writes. `mode: primary` marks a main agent the user starts directly; an adapter's `modes` map replaces same-named fields (OpenCode: `mode: all`). Users override models in `${FACTORY_HOME}/config.json`.
- **Capability tiers.** An adapter declares the tier its harness runs at: 1 native subagents, 2 headless CLI subprocesses, 3 inline (the orchestrator plays each role itself). The approver screen states the tier when it is not 1, since tier 3 weakens reviewer independence.
- **Factory home.** Harness-neutral files live in `${FACTORY_HOME:-~/.factory}`: `pending/`, `improvements/`, `archive/<repo-name>-<branch>/`, user config and the optional `facets-profile.md`. Every harness shares it, so discovery finds runs started anywhere.
- **Agents are stateless.** Every agent turn is a fresh `SPAWN`; nothing relies on continuing a live agent. Whatever a later turn needs is in `state.json` or on disk. This is what lets every harness, and a resume on a different harness, run the same flow.
- **State CLI.** The skill carries `bin/factory`, the factory's single state writer (stdlib Python, thin entry over `bin/factory_cli/`). Read commands (`runs`, `show`, `validate`) do the mechanical discovery and digest work outside the orchestrator's context so routing cost stays flat; write commands (`checkpoint`, `ledger-add`, `wait-open`/`wait-close`, `answer`, `set-status`, `decisions-add`, `verify`, `rebind`, `resume`, `drop`) stamp, validate, write atomically and commit — the orchestrator never hand-edits `state.json`, and a missing Python 3 halts the run instead of falling back to manual writes. `envelope check`, `lock take` and `prune` complete the command surface (gates and hardening below).

## Skill library

The library has a committed repo layer, `skills/`, a per-user layer, `${FACTORY_HOME}/skills/`, and the factory's first-party skills in `core/skills/`, which render verbatim into `dist/<harness>/skills/` ([ADR 0012](docs/adr/0012-first-party-skills-live-in-core-skills.md)) and are linked from there ahead of both other layers. Per-user skills take precedence when names collide, then first-party skills, then vendored library skills. Each selected harness links eligible folders containing `SKILL.md` into its skills root. Dot-prefixed folders are never linked, and `factory` is reserved for the factory skill.

A library link is a symlink whose target starts with the current checkout's `$src/skills/`, the per-user rendered distribution's `$factory_home/dist/`, or `$factory_home/skills/`. Other paths are user-owned and skipped with an adoption hint. A link from another checkout or worktree, or from before the checkout moved, is user-owned: remove the old link and re-run to adopt it. Re-runs prune stale library links before linking the remaining skills. `--add-skill <path>` validates and copies a local skill into the per-user layer. Uninstall removes library links, retaining all layers. Codex and Copilot share `~/.agents/skills`, so uninstalling either removes the other's library links too.

After the harness links are in place, the installer refreshes a browsing mirror of the vendored library in `$factory_home/skills/`: one symlink per `$src/skills/` folder with a `SKILL.md`, created, updated and pruned (stale targets) per run, left in place by `--uninstall` apart from stale-link pruning. Mirror links point at `$src/skills/` and are recognised exactly by that prefix; any other symlink or real folder in the per-user layer remains a per-user skill with per-user precedence. The mirror is browsable convenience, not a layer: the per-user skill scan skips mirror links, so a mirror link can never bypass `SOURCES.md` harness gating or override the vendored link in a harness skill root.

Library and per-user skills are linked, not rendered into `dist/` ([ADR 0009](docs/adr/0009-library-skills-are-linked-not-rendered.md)); the factory's first-party skills render into `dist/<harness>/skills/` ([ADR 0012](docs/adr/0012-first-party-skills-live-in-core-skills.md)). Vendored skills are refreshed manually: maintainers re-copy each upstream skill and update `skills/SOURCES.md`; no sync tool is provided. A `SOURCES.md` row's optional sixth `harnesses` column (comma-separated adapter names, empty = all) restricts which harness skill roots a vendored skill links into; exclusions remove existing links on the next install. Per-user skills are never filtered.

## OpenCode V2 adapter

OpenCode V2 uses foreground `subagent` calls targeting the named `factory-<role>` agent with complete inputs. Parallel dispatch waits for every result; each spawn starts a fresh child session. `SHELL` uses `shell`. Question relay, skill resolution, all nine roles, global/project installation paths and model tiers remain unchanged.

Before creating pending state or a worktree, an OpenCode session must expose both `subagent` and `shell`. If either is unavailable, the loaded skill stops with the missing capability and recovery steps: run `./install.sh --harness opencode`, resolve any conflicting install paths, then start a fresh OpenCode session. Installation verifies the factory skill and all role-agent links and reports that a fresh session is required. This preflight cannot diagnose a session that did not load the factory skill at all.

Before creating pending state or a worktree, inspect the effective installed role selections with the active adapter's supported model inventory. A complete authoritative inventory may identify an unavailable selection and block startup with its exact ID, configuration source and correction/recheck steps. A listed model is not proof of provider access. Failed, partial, unsupported or unresolved inherited inspection is unverified and continues under the existing bounded runtime failure policy. Preserve model/credential choices; never guess an alias or silently substitute. On a later rejection, retain the original diagnostic and recovery steps. Capability-specific inspection belongs in adapters.

Native Markdown emits `mode: subagent` by default and an ordered `permissions` sequence. Read access denies `edit` then `subagent`, while write access denies `subagent`. These rules use the wildcard resource `*`. The renderer appends the design-to-code role's shell approval rules after the access rules. Adapters without a permissions field omit the role-specific rules. The orchestrator alone dispatches roles. Other permissions follow OpenCode configuration. JSON flow mappings inside YAML sequences preserve wildcard quoting without a dependency.

Supported V1 agent and skill definitions remain intended to work through OpenCode's compatibility translation; this is native V2 adoption, not a claim that supported V1 definitions broke. The factory uses neither the plugin nor server API. Existing installer and model overrides still apply; no user configuration migration is needed.

Static rendering verifies output and cross-harness byte compatibility. Historical OpenCode v2.1.4 discovery loaded nine global symlinked roles with expected policy and the factory skill; loading does not establish model-backed dispatch or runtime permission enforcement. Those two checks remain unverified without an actual runtime trial. No new model calls are required for this change, and an observed runtime contract conflict blocks delivery rather than weakening the rules.

## Flow

```
feature
  -> intake: classify exploration vs delivery ("Skill routing"), one question if ambiguous
  -> [idea path] brainstorm         (orchestrator, invoking checkout, writes nothing to the repo)
  -> grilling                       (orchestrator, invoking checkout, writes nothing to the repo)
  -> worktree on NNN-name branch    (orchestrator)
  -> specify -> clarify -> grill-with-docs -> plan -> tasks -> analyze     (spec-builder)
        ^                                                          |
        +------ remediate (patch), then verify loop (max 2 loops) --+
  -> implement                      (design-to-code for [UI] tasks; code-build for the rest, in task order)
  -> build + test verified          (orchestrator)
  -> reviews in parallel            (5 reviewers, UI/UX conditional)
  -> judge                          (review-judge)
  -> fix confirmed findings, re-review (fixer, max 2 rounds)
  -> approver                       (user)
  -> PR                             (orchestrator)
```

Lite chain (DESIGN, "Modes"): specify -> plan -> tasks -> analyze, one pass, no loop; any CRITICAL/HIGH escalates to the full chain from clarify.

## Skill routing

Agreed 2026-10-25 (`docs/superpowers/specs/2026-10-25-factory-skill-routing-design.md`). Uses the right externally-installed skill at the right point in the run, without weakening stateless roles, saved answers, worktree isolation, independent review or publication approval.

### Routing contract

| Trigger                                                                                                                                           | Skill                                                         | Owner                 | First/applied stage                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | --------------------- | -------------------------------------------------------- |
| An exploratory idea without a settled solution — e.g. "I have an idea for...", "explore whether we could...", "not sure yet, but what if..."      | `brainstorming`                                               | Orchestrator          | `brainstorm`, before `grill`                             |
| A concrete feature, change, or an idea already ready to build — e.g. "add a `--no-fast` flag", "fix the resume path so...", a named existing spec | `grilling`                                                    | Orchestrator          | `grill` (idea path's second stage, feature path's first) |
| Neither set of cues, or both                                                                                                                      | — one intent question decides, then routes as above           | Orchestrator          | —                                                        |
| Implementation or repair of code                                                                                                                  | `ponytail` and `tdd`                                          | `code-build`, `fixer` | `implement`, `fix`                                       |
| UI design work with a saved source and scope                                                                                                       | source capability, `design-to-code`, `ponytail` and `tdd`     | `design-to-code`      | `implement`, for `[UI]` tasks                           |
| A UI-related diff enters review                                                                                                                   | `impeccable` audit and critique                               | `ui-reviewer`         | `review`                                                 |
| A user-facing flow changes                                                                                                                        | existing UX lens (complementary, not a repeat of the UI pass) | `ux-reviewer`         | `review`                                                 |

Intake intent is not a stored field: step 0 of `SKILL.md` decides it from the request text, visible afterwards only in the run's first `stage` value and, when a question was needed, in that question's saved relay answer. The idea path is `brainstorm -> grill -> worktree -> the existing spec chain`; the feature path starts at `grill`. Stopping after `brainstorm` leaves the run paused with the confirmed direction in the pending brief and nothing written to the invoking checkout; resuming continues into `grill`, which treats brainstorming's settled decisions as inputs and asks only what is still open. A run saved before this routing existed keeps resuming at its recorded stage unchanged — `brainstorm` is additive to the stage vocabulary (`state.md`), not a replacement of any existing one.

### Skill resolution and precedence

Every lookup is the active adapter's `RESOLVE` operation; machine-specific paths never enter `core/`. `speckit-*`, `grilling`, `domain-modeling` and `pr` resolve at preflight as today. `brainstorming` resolves only on the idea path. `ponytail` and `tdd` resolve at preflight, before a run commits to code delivery, and their absolute paths go to every fresh `code-build`/`fixer` spawn. `impeccable` resolves later, only on a UI diff, through the existing install offer with a disclosed skip. A resume re-resolves any name never resolved and, when `harness` changed, every path. A required missing skill stops the affected work with setup guidance naming it; nothing is installed beyond the existing authorised `impeccable` offer.

Precedence when a skill's guidance and the factory's own rules could conflict: the skill wins, except on the process and hard-defect rules — `ENG-1`..`ENG-5`, `ENG-11`, `ENG-17` and `ENG-23`..`ENG-26` — where `core/skills/factory/references/engineering.md` wins ([ADR 0013](docs/adr/0013-ponytail-governs-change-size.md)). The design-guidance rules `ENG-7`..`ENG-10` and `ENG-13`..`ENG-16` apply only to the code a unit changes, so `ponytail`'s smallest complete change governs how much code a unit adds. In particular, the external `tdd` skill defers refactoring to review, while `ENG-1` permits small behaviour-preserving refactoring of the changed code while tests stay green — the engineering rules govern. A skill's own guidance applies only inside the approved specification: it removes no requirement, security control, accessibility behaviour, planned test, repository tooling or `ENG-n` evidence, and never replaces a role's required result envelope. A skill's own companion references (e.g. `tdd`'s `tests.md`/`mocking.md`) resolve from that skill's own directory, never from the factory or the consuming repository. These rules live here and in each role's own file (`code-build.md`, `fixer.md`, `design-to-code.md` carry the one-phrase precedence bound inline); they are not restated in a separate shared reference.

### Protected confirmations

`tdd` requires user-confirmed test seams before writing tests, and factory roles never talk to the user directly, so `spec-builder` relays the plan's proposed public seams as one question at the end of `plan`, before implementation starts. Relay questions gain an optional `requires_user: true` field (`protocol.md`): fast mode must never auto-answer such a question, alongside the existing `pending_clarify` exclusion; a question saved without the field keeps today's behaviour. The plan declares each seam and its required injected failure paths. Confirmation is persisted separately with the plan (`plan.md`, "Test seams", `Confirmed: <date> - <Qid> accepted - seams: ...; failure paths: ...`) and accepts that exact declared scope. Keep the accepted seam-to-failure-path snapshot in confirmation evidence; a legacy name-only line is reusable only when separate explicit evidence proves the same complete scope. Names alone cannot establish acceptance of newly added failure paths. Adding, removing, renaming or expanding a seam or failure path invalidates it and requires fresh protected confirmation; a plan whose every part is exempt skips the question entirely. Analyze reports HIGH and blocking for any non-exempt task needing an undeclared seam/failure path or missing/stale scope confirmation. `code-build` and `fixer` read the plan's seams, never the confirmation line, and never ask the user: a task needing an unlisted seam is `ENG-4`'s existing stop-and-report failure, not a question.

### Widened UI-change detection

Step 6.1's UI classification (`SKILL.md`) widens from a short extension/directory list to: view markup and styles, design tokens and themes, UI assets (icons, images, fonts shipped to the interface), locale and string files, and a diff whose only change is user-visible copy inside UI code. A diff touching none of these skips the UI passes (`ui-reviewer`, `ux-reviewer`, the `impeccable` install offer). `ui-reviewer` follows `impeccable`'s audit-and-critique route explicitly, running its setup once in the reviewer's own context, staying read-only, and disclosing whether its evidence was rendered or static rather than describing static inspection as an observed interaction; a skipped or evidence-limited UI evaluation is disclosed at the approver gate. `ux-reviewer` keeps its distinct, complementary lens rather than repeating the UI pass.

## Pen design references

Whenever a factory run creates, references, or updates a Pen design intended as an implementation reference, activate the framework-independent [mapping contract](core/skills/factory/references/design-code-mapping.md). Resolve `pen-design` conditionally through the active adapter; a missing required skill or backend capability is a disclosed blocker, not an inferred API. The `design-to-code` role reaches a Pen source only through the pen CLI (`pen` commands, headless `pen interactive`, direct reads of the local `.pen` snapshot), never through a Pen MCP backend offered by the harness. Keep framework-specific guidance separate, starting with [Avalonia](core/skills/factory/references/design-code-mapping-avalonia.md). Standalone Pen invocations outside the factory are outside this boundary.

The repository's canonical `docs/design-code-map.json` supports multiple sources, exhaustive scoped node coverage, canonical components/instances, stable code anchors, explicit removals/exceptions, and reverse lookup from the same records. A design-only task records source/targets without requiring code. Existing implementations bootstrap only the requested scope and dependencies. Persist context in pending storage before worktree creation and under the feature's `factory/design/` afterward; at drop, evidence moves to `docs/design/<branch>/` and map references are rewritten. The permanent map references scoped committed sources, exports, captures, and comparison metadata.

Design governs visual decisions. Default implementation updates to design → code; design edits require an explicit request. Resolve a unique target from the request or saved context/map, and ask on ambiguity. Check source freshness and code anchors on each new/resumed run. Inspect shared consumers, obtain agreement before expanding visual scope, and preserve application behavior when a design element is removed. Unsupported inspection, missing identifiers, or unavailable revisions must be reported honestly.

Mapped implementations require current build/runtime, mapping, and rendered-fidelity evidence independently of optional impeccable evaluation. Exact supported design values and matching viewport/theme/state/DPI/scale comparison are required; no universal pixel threshold is imposed. Static desktop review cannot establish rendered fidelity. Treat a demonstrated violation of the approved reference as a requirement failure, rather than advisory styling preference.

Mapping/visual findings share the existing two automatic fix rounds with all other findings; persist the counter before each design fix attempt so resume cannot reset it. A design gate failure goes through this queue, not a fresh code-build retry for visual repair. Missing prerequisites or exhausted rounds leave work partial/blocked. An explicit, scoped user exception may permit proceeding, while retaining the failed/missing gate and unverified status. Fast mode and ordinary publication approval cannot infer that exception. Non-design runs preserve their existing flow and UI policy.

Fresh spec-builder, code-build, design-to-code, fixer, reviewers, and judge receive the saved `design` context reference. The orchestrator independently checks evidence identity/results, routes protected decisions, and reports design status and exceptions at approval and in the PR. One new write role handles design-to-code because it has its own state machine: discover, survey, plan components, implement batches, validate. No new harness verb, second map, or repair loop is introduced.

Design intake activates and persists context for Pen, Figma, image, and eligible text-only UI requests, including sources discovered later; only Pen requires `pen-design`. At worktree creation every active context moves into `factory/design/context.json`. Figma capability discovery accepts either the existing skill lookup or an available MCP capability, with its usable identity passed to roles. Missing capability blocks rather than triggering installation.

Mixed UI runs persist the active writer and its explicit contiguous task range in design context before spawning, retain them across interruption, partial and protected-question relay resumes, and clear them only after that range finishes. Resume restores this assignment before routing further ranges by `[UI]`; non-design and pre-feature runs keep the existing code-build flow. Settled scope answers persist outside transient relay. A source discovered during any spec stage without active context is reported with its kind, source and scope for activation and same-stage resume. On resume Pen alone requires `pen-design`; Figma rediscovers its skill or inspection capability, while image and text require neither. For legacy context without a source kind, use the recorded source identity to determine it; relay ambiguity rather than guess.

Gate verification accepts legitimately not-applicable gates with their required reasons; text-only mapping and fidelity need no waiver. Before or in the commit completing the last UI task, persist a pending quality-pass marker and its final UI range in design context. While pending, resume that range even when all UI boxes are checked, until the pass outcome and invalidated checks are reconciled. The pass itself is reserved durably before invocation, never started twice on resume, and its applied edits and outcome form a tested commit unit. Affected evidence is invalidated and applicable gates and checks rerun after those edits; clear the pending marker only after those checks are complete.

## FACETS advisor

`factory-facets-advisor` is a **main agent**: the user starts it and talks to it directly. It scores projects and income options against the FACETS checklist (Face, Advantage, Capital, Expertise, Time, Scale), ranks them and discusses follow-ups. The checklist, guidance, calibration examples and source caveats live in `core/skills/factory/references/facets.md`.

- **Not part of the run.** The orchestrator never spawns it. No stage, route, state field, envelope field or CLI change. Principle IV's "agents never talk to the user" covers run agents; this agent talks to the user because it is the session.
- **Starting it.** Role frontmatter `mode: primary`. Claude Code: `claude --agent factory-facets-advisor`. Copilot: `copilot --agent factory-facets-advisor` or `/agent`. OpenCode: rendered `mode: all`, so Tab selects it and other agents can still call it. Codex has no main-agent custom agents and ZCode's support is unverified: there it stays a subagent and `harness.md` says so.
- **Profile.** `${FACTORY_HOME:-~/.factory}/facets-profile.md` (`hours_per_week`, `capital_at_risk`, `skills`, `face_comfort`, `income_goal`, `current_assets`; template `references/facets-profile.template.md`). Missing fields are asked in chat before any research or scoring; the agent saves the profile with `SHELL` only after the user confirms. It is the only file the agent writes.
- **Scoring.** Each of the six verbatim checklist questions scores 1 (yes) or 0 (no), judged against the profile. Advantage keeps its verbatim audience question; a borrowed edge (specialised tool, existing asset, distribution) counts as evidence for yes.
- **Research.** Read-only web research with `WEB_SEARCH` and `WEB_FETCH`, at most 3 searches and 5 fetches per option, stopping early once all six facets have cited evidence. A facet still unknown scores 0 and is marked unverified.
- **Verdict.** 6 = pursue; 4-5 = investigate, naming each "no" and the cost of fixing it; 3 or less = drop. A Capital 0 whose likely loss exceeds `capital_at_risk` caps the verdict at investigate. Ranking sorts by total, then breaks ties by Capital, Time, then Scale; options still tied stay tied with a reason.
- **Output.** Markdown in chat: a checklist table per option (answer yes, no or no (unverified), why, sources with vendor sources marked), a ranking table with each option's search and fetch counts, and the source caveats, which always note the framework's origin in a sales funnel. Follow-ups rescore only what changed. Results are not saved.

## Agents

| Agent                       | Tier     | Access | Role                                                                           |
| --------------------------- | -------- | ------ | ------------------------------------------------------------------------------ |
| `factory-spec-builder`      | deep     | write  | Runs specify through analyze, one stage per spawn; remediates analyze findings |
| `factory-code-build`        | standard | write  | Runs speckit.implement against tasks.md; must finish green                     |
| `factory-design-to-code`    | standard | write  | Implements UI design tasks in dependency batches with design evidence; also a standalone main agent for design-to-code work |
| `factory-security-reviewer` | standard | read   | Security review of the diff                                                    |
| `factory-code-standards`    | standard | read   | Diff vs the repo's documented conventions                                      |
| `factory-spec-conformance`  | standard | read   | Diff vs spec, plan, tasks                                                      |
| `factory-ui-reviewer`       | standard | read   | impeccable audit + critique of changed UI (UI diffs only)                      |
| `factory-ux-reviewer`       | standard | read   | UX flows, states, copy (UI diffs only)                                         |
| `factory-review-judge`      | deep     | read   | Merges, dedupes, verifies findings; one verdict                                |
| `factory-fixer`             | standard | write  | Fixes confirmed findings or the user's requested changes                       |
| `factory-facets-advisor`    | deep     | research | Main agent: scores and ranks projects or income options on FACETS; never spawned by the orchestrator |

On Claude Code, `deep` is opus and `standard` is sonnet.

Agents cannot spawn agents, so the "reviewer agent" is the **judge**: the orchestrator fans out the reviewers and hands their output to the judge.

All reviewers return the same findings shape (`core/skills/factory/references/findings.md`).

## Decisions

### Setup

- **Missing `.specify/`**: offer to run `specify init --here <harness.speckit_init>` — each adapter states its own `speckit_init` arguments (ZCode's: `--integration zcode --integration-options="--skills"`) — then the constitution step. Ask once.
- **impeccable missing**: ask once, then `npx impeccable install --providers=<harness.impeccable_provider> --scope=global`.
- **Skills that block model invocation**: every `speckit-*` skill and `grill-with-docs` set `disable-model-invocation: true` (or are commands rather than skills on some harnesses), so no agent invokes them. Agents read the resolved file and follow it as instructions. `grill-with-docs` runs as its two parts: `grilling` + `domain-modeling`.

### Isolation

- Grilling runs in the invoking checkout and writes nothing to the repo. Its output (`brief.md`) and pre-run state live under `${FACTORY_HOME}/pending/` until the worktree exists.
- The branch name comes from SpecKit's git script in `--dry-run` mode. The factory creates a git worktree on that branch, and everything after grilling runs inside it.
- The spec directory is passed explicitly (`SPECIFY_FEATURE_DIRECTORY=specs/<branch>`), so branch and spec folder always match.
- SpecKit extension hooks are skipped: the factory owns the branch and every commit.
- Several runs may go at once in one repo, one per session. Branch creation reserves the number, so a later dry-run sees it.

### Modes

- **Chain** (`full` | `lite`), recorded in `state.mode.chain`. Default `lite`: a run starts on the lite chain unless a flag pinned it (`--lite` pins lite, `--full` pins full; the last one wins). Grilling's closing summary names the chain in effect and the user's confirmation covers it — an objection flips it to `full`, which the orchestrator recommends when the feature's size calls for it. `lite` = specify → plan → tasks → analyze, one pass, no loop: clarify and grill-with-docs are skipped (the top grilling captured what they would have). Any CRITICAL/HIGH analyze finding escalates: the chain becomes `full` and continues from clarify (clarify, grill-with-docs, then plan and tasks re-derived, then analyze under the normal loop rules). MEDIUM/LOW: remediate once, then implement. Every stage keeps its checkpoints, so a lite run resumes like any other.
- **Fast** (`state.mode.fast`, on by default; `--fast` pins it on, `--no-fast` turns it off, the last one wins): the orchestrator auto-accepts every relay round with the agent's recommended answers, recorded with `"auto": true` in `state.relay`, collapsing multi-round stages to agent-only turns. Never auto-answered: questions in `state.analyze.pending_clarify` (a patch that overturns a decision is the user's to make), and every halt — loop exhaustion, red build, agent failure, `--stop-at`. The approver screen lists the auto-accepted rounds for veto.

### Interactive steps (relay)

- Grilling at the top runs in the orchestrator directly. It uses the same question presentation and reply rules as later relays and stays interactive even in fast mode.
- Work the design tree in rounds. Each round contains the **whole frontier**: every open decision whose prerequisites are settled. Defer questions whose wording or options depend on unanswered decisions; recompute the frontier after the round is answered.
- clarify, grill-with-docs, and specify's clarification markers run inside spec-builder. When spec-builder has questions it ends its turn with the whole frontier (with recommended answers). The orchestrator saves every answer to state as it arrives, then spawns a fresh spec-builder for the same stage. That role reads every round from `state.relay`, treats answered questions as settled, and asks only what is still open. Relay restarts and resume use the same path.
- **Presentation** is chat Markdown on every harness, even for one question: `🧭 Question N of M · Qid`, a `❓` question heading, helper text, lettered options with meaningful emojis and short descriptions, an `✨ AI suggested` marker on the recommended option, and a `💡 Suggested answer` block with the answer, a concise `🎯` rationale grounded in known context, and a textual `✅ Use suggested answer: Qid: accept` shortcut. Separate questions with horizontal rules. N/M counts positions in the current round; Qids remain unique within the stage across rounds. Shortcuts are text, not interactive buttons.
- **Custom answers**: each choice question includes a final `💬 Something else` option. Use free text without artificial choices for open-ended questions; their recommendation may be proposed text.
- **Replies**: accept `Q7: B`, `Q7: <custom text>`, and `Q7: accept`. Bare `accept` fills only unanswered questions with their recommendations, preserving explicit answers. Bare option letters are valid only when exactly one question remains unanswered. Clarify ambiguous replies before assigning them; save each unambiguous answer immediately.
- **Compatibility**: keep existing saved answers and IDs. New question fields support helper text, structured option descriptions/emojis, and a separate recommendation rationale. Read old question shapes too, showing available information in the new layout without inventing missing descriptions or rationale. Accepted answers contain the selection or proposed text, separate from its rationale. Fast-mode eligibility stays unchanged, including the `pending_clarify` exclusion.

### Analyze loop

- After analyze: if any CRITICAL or HIGH finding exists, spec-builder **patches every finding at every severity in place** (remediation edits `spec.md`, `plan.md`, `tasks.md` and the other artifacts; it never regenerates them). Findings that need a user decision become clarify questions instead of silent fixes. Then analyze **re-runs against the patched artifacts** (pass + 1) to confirm the fixes.
- clarify and grill-with-docs re-enter the loop only when a remediation finding was deferred to clarify (a decision-touching patch): the pending questions are answered, the settled decisions are edited into the artifacts, and analyze verifies again. A loop whose patches touched no decision re-runs analyze alone.
- At most 2 loops. If CRITICAL/HIGH findings remain after the second loop, halt and ask the user: proceed, give guidance for one more pass, or abort.
- If analyze reports only MEDIUM/LOW findings: remediate once (patches in place), then go straight to implement (no loop).

### Implement

- On a UI design run, route `[UI]` tasks to `design-to-code` and all other tasks to `code-build`, preserving `tasks.md` order. Other runs retain the existing `code-build` flow.
- **Commit unit**: one behavior-changing task contains the observed failing-test step, implementation and passing checks under one checkbox. Commit it once with tests and implementation together and the required red proof. Generation, analyze, execution, fixing and review use this same unit. On resume, inspect worktree and commit evidence and continue the unfinished unit; preserve completed work. Unambiguous legacy adjacent test/implementation entries jointly form one unit and finish together; ambiguous pairing stops before behavior changes.
- code-build reads build and test commands from the repo's CLAUDE.md / AGENTS.md, falling back to detection.
- Done = every task in tasks.md checked, build green, tests green. The orchestrator re-runs build and tests itself to verify. Still red after code-build's own attempts: one fresh code-build gets the failing output; still red: halt and ask.

### Review

- Always: security, code-standards, spec-conformance.
- Only when the diff touches UI files: UI (impeccable) and UX.
- Round 1 reviews the full diff. Every later round is a **delta review**: reviewers see the fix diff since the previous round's checkpoint together with the previous verdict, and check that the fixes landed and added nothing. The fixer declares every file it touches beyond the findings' own files as `Adjacent: <path> - <reason>` in its commit body; the judge checks the fix diff's file list against the findings' files and those lines, and its verdict can carry `escalate`, which re-runs the round once in full review.
- The judge merges, dedupes and verifies. Confirmed blocking findings go to the fixer; then build + test, then a delta re-review. At most 2 fix rounds. Advisory findings go to the approver untouched.

### Approver

Shows summary, diff stat, spec link, judge verdict, fixed findings, remaining advisory findings, the capability tier when it is not 1, and (when `mode.fast`) the auto-accepted relay rounds. Options:

- **Approve**: push and open the PR.
- **Request changes** (free text): fixer, build + test, re-review, back to the approver. No cap; the user drives it.
- **Abort**: keep the worktree, state `aborted`.

### PR

Push the branch, open a ready-for-review PR against the default branch with `gh pr create` and a body written via the `pr` skill (links the spec, includes the review summary). Run `factory set-status pr-open --pr-url <url>`, then `factory drop` to archive the run folder and create `factory: drop run artifacts`. Push again, retrying once on failure; if both pushes fail, notify the user to run `git push` from the named worktree. Notify the totals sentence and PR URL from the drop JSON. The worktree is kept until the branch merges. Harness-specific extras (on Claude Code, offering the desktop app's Auto-fix binding) come from `harness.md` and are offered, not automatic.

### State and resume

- Recheck effective model setup when the harness or model configuration changes; retain exact choices and prior rejection evidence. Carry pending mandatory verification across partial handoffs; no unfinished check counts as passed.
- State lives at `specs/<branch>/factory/state.json` inside the worktree (schema: `core/skills/factory/references/state.md`). It records the `harness` running the run; each `history` entry records the harness that wrote it.
- One checkpoint commit per stage (`factory: <stage> complete`) plus a state update. Implement additionally resumes per task from the tasks.md checkboxes.
- Resume restarts the interrupted stage from its beginning. A relay in progress resumes from the saved Q&A: a fresh spec-builder gets the answered questions and asks only the rest.
- A run may be resumed on a different harness: the orchestrator re-resolves every skill path.
- `--stop-at <stage>` (on a new run or a resume) pauses the run cleanly before that stage starts: checkpoint, `status: paused`, notify, end the turn. A `--stop-at` stage the chain never reaches (e.g. `clarify` on a lite run that never escalates) never triggers. `resume <branch>` (with the harness's invoke command, e.g. `/factory` or `$factory`) continues from that stage in any session, on any harness. Flags on a resume update the run before the stage restarts: `--lite` / `--full` rewrite `mode.chain`, `--fast` / `--no-fast` rewrite `mode.fast`.
- Plain `/factory` lists unfinished runs in the current repo (`bin/factory runs`, scanning `git worktree list` plus `${FACTORY_HOME}/pending/`) and offers to resume one; `/factory <feature>` starts a new run. `resume <branch>` fetches a resume digest (`bin/factory show`) — scalars plus aggregates, never the whole state — and restarts the recorded stage from it.

### State CLI (v4)

- **Analysis recording repair**: `analyze-record <envelope>` is the writer for completed analysis outcomes. Accept a bare JSON envelope or its final fenced JSON block, validate non-negative integer severity counts and an existing report confined to this run's spec directory, normalize spec/worktree-relative paths to spec-relative form, append each report once, and store the latest counts/report with a writer timestamp in optional `analyze.result`. Preserve loop counters, remediations and pending clarification questions. Commit through the existing locked, atomic state writer; invalid input leaves state and HEAD unchanged. The orchestrator records this outcome before its analysis checkpoint, not by editing state or inventing a gate override.
- **Writer layout**: `bin/factory` stays a thin entry script (argv → `factory_cli.cli.main`, exit codes preserved); all logic lives in `core/skills/factory/bin/factory_cli/` modules (`__init__`, `cli`, `state`, `lock`, `checks`, `totals`, `commands`), which the renderer's `copytree` already carries into every `dist/<harness>/skill/` unchanged. Every state mutation goes through it; the orchestrator never hand-edits `state.json`, and a missing Python 3 halts the run with a clear message instead of falling back to manual writes.
- **Schema v4**: `version: 4` adds an append-only `decisions` list and per-spawn `started_at`/`ended_at` intervals; the history-event vocabulary is closed — `complete`, `verify-pass`, `verify-fail`, `approved`, `gate-override`, `aborted`, `pr-open`, `resumed` — and anything else is a validation violation with its location. Readers accept versions 1–4 including legacy relay shapes and report, never rewrite, what they read; the writer upgrades a run to v4 in the same atomic write that first changes it (temp file + `os.replace`).
- **Effort accounting**: agent time is the union of ledger spawn intervals, human time the union of recorded user-wait intervals (`at` → `answered_at`), both reported separately; overhead derives as `max(wall − human − agent, 0)`. No report sums parallel durations or subtracts summed durations from wall clock, so human + agent never exceeds wall time by construction.
- **Test layout**: a new `tools/tests/` package (one module per seam plus `fixtures/`) that `python3 -m unittest discover -s tools` discovers unchanged. Runs 005 and 006's saved states are recovered from git history as replay fixtures, each with a defect manifest naming stability-brief §3's core defects the replay must report.

### Enforced gates (M2)

- **Fresh-state gate decisions**: checkpoint evaluates its transition gate and permitting decision inside the writer's lock against the freshly re-read state. A newly recorded CRITICAL/HIGH result blocks implementation without an explicit override; pending clarification questions still block independently. Older states without `analyze.result` retain their existing gate behavior.
- **Lock lifecycle**: every write acquires `lock.json` beside the state it guards — `<worktree>/specs/<branch>/factory/lock.json` for a worktree run, `<pending-name>.lock.json` beside the pending file before that — recording owner PID, host, harness and time. A write under a live foreign lock is refused with the owner reported; a lock is stale only on its recorded host when the owner process is gone (`os.kill(pid, 0)`), never automatically elsewhere; `factory lock take <run> [--force]` is the only takeover and records `taken_over: true` with the previous lock for audit (FR-005).
- **Gate table**: `factory_cli/checks.py` holds one table checked by `checkpoint` before the write that advances a stage: → `review` requires the latest verify record to be `verify-pass` with every recorded command passing; → `implement` requires analyze clean, remediated, or an explicit override decision; → `pr` requires an `approved` decision recorded at `approver` (or a `gate-override`). Refusals name the missing or invalid record. `factory verify --pass|--fail --commands '<json>'` writes the verify record. A pass requires a non-empty command list with a command name and a status of integer `0` or `"pass"` for each entry. `decisions-add --kind approved|gate-override` records the decisions. The transition a gate decision permits also gets an `approved`/`gate-override` history entry carrying that decision's question ID. Every history event keeps exactly one writer (FR-006).
- **Role-output shapes**: `envelope check <file>` validates a role output's final fenced `json` block against the three shapes — envelope (protocol.md), reviewer report and judge verdict (findings.md). Key sets, types and required fields are encoded once in `checks.py` with the references' own fenced examples as passing fixtures; one malformed variant per shape is refused with the offending location. Malformed output enters the retry-once policy (FR-007).
- **CI**: `.github/workflows/ci.yml` runs the full suite, re-renders all five harnesses and fails if `dist/` is tracked (`test -z "$(git ls-files -- dist/)"`; `dist/` is git-ignored build output, constitution III v2.0.0), and checks `install.sh` syntax with `bash -n` (FR-018).

- **Model policy**: `claude-code`, `codex` and `opencode` ship explicit tier selections from their `adapter.json`; preserve those shipped mappings (including Claude Code's haiku standard tier). `copilot` and `zcode` inherit session models. The adapter mapping is authoritative; documentation and tests check that policy without silently replacing selected model IDs. Personal choices live in the user's `${FACTORY_HOME}/config.json` under `models.<harness>`; they merge only into the per-user render that `install.sh` creates at `${FACTORY_HOME:-~/.factory}/dist/<harness>` (`render.py <harness> --out`), never into the canonical `render.py <harness>` render or the git-ignored `dist/`. `install.sh` prints the effective model per role resolved from the default home, and a render-seam test keeps the README's statement aligned with `adapters/` (FR-015).

The installed CLI ships `adapter_models.json`, parity-tested against the authored adapter mappings. `factory models [--json]` reports effective values and sources; `factory init` seeds project config and a README without overwriting config. `/factory init` routes to that CLI and stops. Preflight records a state `models` block containing per-tier `resolved` values and `source` labels, and supplies the resolved tier to each spawn.

### Cost ledger

- Every `SPAWN` (each role of a `SPAWN_PARALLEL` counts as one) appends one entry to `state.ledger` (schema: `state.md`): stage, role, harness, input/output token estimates, harness-reported usage when available, duration.
- Estimates are harness-neutral: 1.35 × word count of what the spawn was told to read (its role file, the resolved skill files, the artifacts its inputs name) and of what it wrote (the returned envelope plus new files under the spec's `factory/` folder).
- `reported` is reserved for usage the harness exposes (today: none in tier 1; tier-2 CLI output where the harness prints it). Every efficiency change to the flow is measured against a prior run's ledger, not guessed.
- The ledger's own cost is one `wc -w` and one state write per spawn.

### Time budget, issues, improvement backlog, benchmark

Agreed 2026-10-27 ([spec](specs/010-agent-time-budget/spec.md)). Every spawned agent works inside a time budget; everything that went wrong becomes a session issue; the improvement backlog exists only after its run is over; factory versions can be benchmarked before and after.

- **Time budget**: `${FACTORY_HOME}/config.json` carries `budget: { default_s: 300, roles: { <role>: <seconds> } }` — 5 minutes by default, one positive-integer override per role; a missing or unusable value falls back to 300 per entry and never fails the run. The orchestrator resolves `factory budget <role>` before every spawn and passes the absolute `deadline` (ISO UTC, now + seconds) in that spawn's inputs. The budget binds spawned roles only: reviewers and the judge are never stopped (their overrun is recorded after the spawn finishes), and orchestrator verify time over budget is recorded with role `orchestrator` without stopping anything.
- **Deadline stop**: the file-writing roles (spec-builder, code-build, design-to-code, fixer) check remaining time at safe commit-unit boundaries before starting more work. Avoid optional repeated broad verification when observed duration cannot reasonably fit, or fit is uncertain near the deadline. When a required broad check cannot reasonably fit its observed duration, hand it off explicitly as pending rather than starting an avoidable overrun. A fresh role starts pending mandatory verification as its next unit even when its observed duration exceeds a full fresh budget, then finishes that in-flight check safely; repeated deferral is not progress. All work/checks already complete permits done without an optional repeat. Required checks remain pending across handoff and must pass before review; mandatory role checks and independent orchestrator verification remain required. Partial summaries name the next unit and pending required checks. Keep budgets, actual overshoot records and stall enforcement unchanged. Past the deadline they finish the unit in flight, commit that progress, and return `partial` with an `overrun` report `{ "cause", "detail" }` — `cause` from the closed list `large-input`, `test-loop`, `retry`, `tool-slow`, `scope-too-big`, `other`; `detail` carries the overshoot past the deadline. `partial` is valid from all file-writing roles. The orchestrator re-spawns a fresh agent with the same inputs, which resumes from the work on disk.
- **Overrun detection and recording**: after every spawn, `factory ledger-add ... --overrun '<json>'` carries the role's self-report; a self-report wins, else a ledger duration over the role's budget yields cause `unreported`, and an overrun both self-reported and detected is recorded exactly once.
- **Session issues**: run state schema **v5** adds one append-only top-level `issues[]` (readers accept 1–5; first write upgrades additively). `factory issue-add <kind> <stage> <role> --detail --duration-ms [--cause] [--commit] [--partial-return]` appends one record per event; `kind` ∈ `overrun`, `agent-failure`, `retry`, `halt`, `verify-fail`; `--cause` is required for `overrun` (closed list above plus the detected-only `unreported`), null otherwise. Every `partial` return whatever its stop reason is recorded exactly once — a deadline stop as `overrun` (self-report or `unreported`), any other stop (e.g. low context) as `retry` — marked `partial_return: true`. A failure-policy retry is not a partial return: its `retry` record is unmarked and never counts. `set-status halted` records `halt`; `verify --fail` records `verify-fail`.
- **Stall cap**: `issue-add`/`ledger-add` results carry the stall rule over every record marked `partial_return: true` of one stage: `consecutive_no_commit` counts trailing marked records sharing one `commit`; any new commit resets it; at 3 (`cap: 3`) the result says `halt: true` and the orchestrator runs `set-status halted`. Records of never-stopped roles never carry the mark, so they never count.
- **Gated improvement backlog**: on `set-status pr-open|aborted` the writer exports `${FACTORY_HOME}/improvements/<repo-name>-<branch>.json` atomically (temp + rename): the run's issues verbatim, `factory_cli.totals.compute` output, the factory version (`factory_sha`, best-effort, `null` outside a git tree), `status: "ready"`, `exported_at`. Zero-issue runs export too — the file's existence is the structural gate, so it never exists before its run ends. `factory improvements` lists ready backlogs with kind counts and a `suggested_feature` text; `factory improvements claim <name>` stamps `claimed`/`claimed_at` once, refusing an unknown name, a non-`ready` status, or a discoverable source run that has not ended (the refusal names that run). Starting an improvement run stays manual (`/factory improve` lists and stops).
- **Benchmark**: `tools/bench.py` replays the pre-settled fixture feature `conformance/bench/greet-001/` headlessly (`claude-code` → `claude -p <prompt>`, `opencode` → `opencode run <prompt>`, anything else refused by name), stops at the approver gate — no auto-approve, no PR. `run` takes `--model` (forwarded as `claude --model <m>` / `opencode run -m <m>`; absent means no model option) and `--from-checkout` (renders this checkout via `install.sh` into `<out>/home` and `<out>/harness-config` and launches against it; exclusive with `--home`). A Claude Code run carries a scoped grant, never a bypass mode: `--add-dir` for the run output directory, the skill directory in use and `--home` when it lies outside, plus `--allowedTools Read Edit Write Agent Skill Bash(git:*) Bash(python3:*) Bash(<skill_dir>/bin/factory:*)`. `<out>/provenance.json` is written before launch (checkout revision and changed paths, render or installed-factory digest, harness versions), and each `score` entry carries its run's record under `provenance` (a missing or mismatched record is marked, never changes `pass`). `score` reads recorded state through `factory_cli` (`state`/`totals`/`checks`, one source of truth) and emits wall/agent/human time, spawns, overruns, issues by kind, token estimates, review/fix rounds, and the four pass conditions `reached-approver`, `last-verify-green`, `no-blocking-findings`, `fixture-acceptance` — `pass` only when all four resolve; an unmet condition scores a fail naming itself; the scorer never raises. `compare` prints the per-metric delta between two scores. The manual fallback (run the factory on the fixture, then `score`) is documented for environments without a headless harness; live runs stay manual and token-costing, and the automated suite scores recorded states only.

#### Post-run retro

Between `set-status pr-open` and `drop`, a read-only standard-tier `retro` role receives `factory show` JSON, the read-only `state.json` path, analyze report paths, verdict paths and `covered_keys`. It skips missing sources and covered keys, and ranks at most three signals: halt clusters (2+ halt, agent-failure, retry or overrun issues in a stage); judge rejections (2+ findings for a reviewer, at least half rejected); recurring fixer classes (blocking in 2+ rounds or 2+ times in one round, class = first cited `ENG-n` in evidence, lower-cased; no citation means no class); analyze escalation (any report with CRITICAL or HIGH > 0); and in-est outliers (role maximum at least twice the run-wide median with 4+ ledger entries). Impact order follows that list, ties by count. Keys use `<kind>:<subject>`, with subjects matching `[a-z0-9][a-z0-9-]{0,63}`.

The role returns `retro.candidates` in its envelope, each with `signal_key`, `rank`, `evidence` and a one-line `suggested_feature` usable unchanged as `/factory <feature>`. `factory improvements add --from <file> --run <branch>` validates candidates, deduplicates against ready entries, caps each run at three, and writes atomically under a home-level lock; it reports `written`, `skipped` and `dropped` as JSON. Each new Retro entry is named `<repo-name>-<branch>.<repo-hash>.retro.<kind>.<subject>.json`, where `repo-hash` is the first 12 hex digits of SHA-256 of the full repository path. Existing own-run entries retain their names; a destination collision is refused rather than overwritten.

`ledger-add` and `issue-add` accept stage `retro` on a `pr-open` run; other ended-run writes remain refused. Every spawn, including failed attempts, is ledgered. A retro ledger entry is a re-entry marker checked only on sub-step entry, not between retries. Failure gets one fresh retry, then a skip without halting; the final notice names skips and failed writes. A run interrupted between `pr-open` and the final push requires manual recovery: run `factory drop` from the worktree, then `git push`.

### Policies

- Agent failure (crash, unparseable output, timeout): retry once with the error attached, then halt and ask.
- Notification (`NOTIFY`, a no-op where the harness has none) on every wait for the user: relay questions, analyze-loop exhaustion, red build, agent failure, approver.
- `speckit.checklist` and `speckit.taskstoissues` are not part of the flow.

## Engineering discipline

The factory's coding discipline lives in one shared, harness-neutral reference: `core/skills/factory/references/engineering.md`, addressed by roles as `<F>/references/engineering.md`, carrying the stable rule ids `ENG-1`..`ENG-31` ([ADR 0001](docs/adr/0001-factory-owns-its-engineering-rules.md)). Every role that writes, plans, reviews or judges code points at it and restates no rule inline.

Professional code is correct, readable, maintainable, secure, and fast enough for its requirements. The 2026-10-25 revision preserves the original eleven ids and the factory's test-first/commit process, refines clean code, SOLID, reuse and functional preferences to require judgement, and extends the reference to cover the user's 34-practice checklist: problem understanding; KISS/YAGNI/DRY; cohesion, coupling and contracts; types, state and errors; trustworthy tests and incremental refactoring; measured performance, data access and concurrency; resource limits, security and integrity; dependencies, automation, reviewability, observability and safe delivery. Apply relevant practices to the actual change. Do not require an interface, abstraction, service, cache, benchmark or new tool without a concrete need.

- **Red proof**: the red step is recorded as one `Red:` line in the task's own commit body, in one of the two accepted forms; there is no separate red commit, so history stays bisectable ([ADR 0002](docs/adr/0002-red-proof-lives-in-the-task-commit-body.md)).
- **Test seams**: the plan settles, at plan time, the public seams put under test and any test-first exemption with its reason; an implementing or fixing role never invents a seam — it stops and reports a missing one as a failure ([ADR 0003](docs/adr/0003-test-seams-are-settled-at-plan-time.md)).
- **Enforcement**: `code-standards` enforces the rules on the code (diff), `spec-conformance` checks red proofs against `tasks.md` (and fix commits against the prior round's verdict), and the judge verifies and rates findings by rule id.
- **Precedence**: a consuming repository's constitution or documented conventions win; the plan records `Overridden: ENG-n - <repo rule that wins>`.
- **Judgement-call ceiling and advisory route**: a finding based only on design or style guidance, including `ENG-7`..`ENG-10`, is at most MEDIUM and never blocking, lowered rather than dropped. Similar-looking code or a missing speculative abstraction is not by itself a defect. A concrete correctness, security, integrity, resource, performance-requirement or documented-contract failure is rated by its demonstrated consequence and cites the relevant requirement or engineering rule; it is not downgraded because the same code also raises a design preference. The factory's test, red-proof and seam requirements keep their existing enforcement. A capped finding is advisory: no verdict-driven fix round acts on it, it reaches the user in the verdict's advisory list, and the approver's existing "Request changes" is the user's route to having it fixed ([ADR 0004](docs/adr/0004-judgement-call-rules-advise-they-never-block.md), refined 2026-10-25).
- **Stop on an un-runnable test command**: a repository with a test runner whose test command cannot be run is a stop, not an exemption. Both code-writing roles return a failure naming the command and its error and ride the orchestrator's existing failure policy, writing no behaviour-changing code and no third form of red proof.
- **Plan-time reason line**: the plan states a reason for each new file, new abstraction and new dependency it introduces; analyze reports a MEDIUM, non-blocking finding for a missing one.

Reuse existing tools and checks. Reviewers apply the relevant shared rules within their lenses; omissions are findings only when supported by a requirement, risk or demonstrated defect.
